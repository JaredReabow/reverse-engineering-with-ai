# Methods for reverse engineering encrypted firmware and software

This survey covers 31 complementary methods for recovering structure, plaintext, keys or behavior. Each method states an experiment and an acceptance standard. Choose methods according to the available access and the required result. The catalogue is broad, not a claim that every technique or platform is covered.

Start with the [investigation workflow](workflow.md) and [evidence framework](evidence-framework.md). Use the [AI collaboration guide](ai-collaboration.md) to keep generated interpretations tied to reproducible observations.

For any investigation, first record five things:

- **The representation being examined:** downloaded package, extracted component, logical partition, physical flash dump, or runtime memory.
- **The required result:** one plaintext image, a reusable content key, a device/root key, an explanation of behavior, or a reconstructed executable.
- **The available access:** files only, readable updater, executable environment, enabled diagnostics/debugging, or physical hardware.
- **The unresolved dependency:** missing format information, compression dictionary, base image, key, hardware service, or runtime state.
- **The independent validation:** an original authentication tag, a trusted expected digest, a reference execution, or another observation that could disprove the hypothesis.

That record prevents several methods from being pursued against the wrong layer. The tables retain the original numbering.

For **artifact acquisition, format reconstruction, and static analysis**, the strengthened methods are:

| Method | Stronger analytical procedure | Validation and main limitation |
|---|---|---|
| **1. Alternative artifacts** | Build a release matrix covering model, hardware revision, region, version, update channel and package type. Look for full updates, recovery images, development builds and readable older components. | Establish equivalence using a trusted target digest or an independently recovered counterpart. A readable older version is otherwise a reference for behavior; it cannot be directly compared with still-encrypted code. |
| **2. Vendor source, SDKs and build tools** | Examine packaging scripts, linker scripts, generated configuration, format definitions and exact compiler/library versions. Reproduce a small relevant component when possible. | Compare generated structures or functions with the actual artifact. Public source may omit proprietary processing or describe another product revision. |
| **3. Recursive extraction** | Maintain a map of source offsets, lengths, nested containers and unexplained residual regions. Record which extractor and parameters produced each result. | Require consistent boundaries, complete stream consumption where appropriate, and independent checks of the extracted structure. A tool successfully writing files does not establish that it extracted the entire image. |
| **4. Sparse, delta and storage reconstruction** | Identify which bytes are supplied, copied from a base image, filled, omitted or generated. For deltas, establish the exact source build before applying operations. | Check the reconstructed target against trusted expected partition information. Mark unspecified or unavailable regions explicitly; synthesized filler is not recovered evidence. |
| **5. Statistical and structural triage** | Compare entropy at several window sizes alongside repetition, alignment, strings, block patterns and format boundaries. Use the results to rank hypotheses. | Confirm a hypothesis through a parser, consumer implementation or successful transformation. Entropy cannot identify a cipher or distinguish all compressed data from ciphertext. |
| **6. Reverse the updater or loader** | Follow actual dataflow from package input through parsing, key setup, transformations, verification and output. Separate update cryptography from unrelated networking or storage cryptography. | Confirm the recovered pipeline against a real artifact or observed execution. Finding crypto constants or a function called “decrypt” is only a lead. |
| **7. Reconstruct KDFs and key wrapping** | Draw the dependency chain from root secret or password through derivation/wrapping to content keys. Record byte encodings, salts, context values, counters, nonces, tags and associated data. | Validate the resulting key and parameters against independent cryptographic evidence. Correct field lengths establish structure, not successful derivation or unwrapping. |
| **8. Version and known-code comparison** | Compare corresponding layers and account for compiler, architecture, optimization and library changes. Inspect relevant operands, constants and side effects in candidate matches. | Confirm important matches through behavior or detailed semantics. Similarity scores and shared function names do not prove equivalence. |
| **9. Simple obfuscation and weak transforms** | Derive a consistent transformation hypothesis from the reader or recurring structure. Check position dependence, key periods and reset boundaries. | Validate on regions or artifacts not used to infer the transform. A few recovered strings or one correct magic value can be accidental. |

The format reconstruction changes matter in practice. Android’s update metadata explicitly distinguishes full payloads from deltas requiring a particular source version, and records the operations and partition information needed for reconstruction. unblob’s reports help preserve the relationship between extracted objects and their original byte ranges. [Android update metadata](https://android.googlesource.com/platform/system/update_engine/+/refs/heads/main/update_metadata.proto), [unblob guide](https://unblob.org/guide/)

**Compression needs a stronger place in the workflow.** Raw DEFLATE can have no zlib/gzip header or built-in checksum, and may depend on a dictionary supplied separately. A zlib-wrapped stream can identify a preset dictionary; a raw stream does not provide the same identification mechanism. Consequently, failed decompression may mean the wrong wrapper, dictionary or starting state. Decrypted data can also remain high entropy because it is still compressed. [zlib manual](https://zlib.net/manual.html)

Static crypto identification also needs more than recognizable lookup tables. Implementations can use bitslicing or processor instructions, so the absence of familiar AES tables does not exclude AES. Follow inputs, outputs and dependencies. [BearSSL implementation discussion](https://www.bearssl.org/constanttime.html)

For **runtime analysis and reconstruction of software behavior**, the strengthened methods are:

| Method | Stronger analytical procedure | Validation and main limitation |
|---|---|---|
| **10. Debugging and API instrumentation** | Observe the relevant transformation boundaries, including successful return, buffer lengths and key-handle use. Establish whether the process contains actual key bytes or merely requests operations elsewhere. | Validate captured plaintext or keys independently. Instrumentation can recover any secret actually present in observable software—including a root key—but cannot assume visibility into protected hardware. |
| **11. Runtime unpacking and snapshots** | Treat unpacking as a timeline. Record when regions appear, change, become executable or disappear, and which application features were exercised. | Maintain a coverage map of captured and missing regions. A single snapshot may contain only part of the program; coherent disassembly is weak evidence alone. |
| **12. Executable reconstruction** | Preserve the relationship between file offsets, virtual addresses and runtime mappings. Reconstruct applicable imports, relocations, resources and initialization metadata. | Distinguish an image useful for analysis from one that is runnable. Loading successfully is an initial check; representative reference behavior is needed to assess fidelity. |
| **13. Emulation and rehosting** | Start with the smallest useful unit: a parser, decryptor or library before an entire device. Document every external dependency and every simulated response. | Compare outputs and state transitions with independent observations. A substitute hardware function can make execution proceed while invalidating the conclusion being tested. |
| **14. Symbolic, concolic and taint analysis** | Work backward from the output of interest and constrain analysis to relevant inputs and code. Record environment assumptions and function summaries. | Replay generated inputs or solver results concretely. Path explosion limits coverage; inaccurate summaries can produce results the real implementation cannot reach. |
| **15. Deobfuscation and devirtualization** | Recover dispatcher state, virtual instructions, handler effects and hidden state separately. Preserve arithmetic width, flags, memory effects and exceptional behavior. | Compare reconstructed behavior on additional inputs and paths. Simplifying arithmetic handlers does not establish recovery of an entire virtualized application. |
| **16. Managed code and scripts** | Identify the exact runtime and representation: IL, DEX, JVM bytecode, script bundle, cache, native extension or AOT output. Follow dynamically loaded components where accessible. | Check reconstruction against the lower-level representation and observed behavior. Readable source-like output does not recover lost comments, names, unshipped server code or protected secrets automatically. |
| **17. White-box cryptography and DCA** | Determine which inputs, intermediate states and traces are observable, then test whether the implementation exposes useful key-dependent relationships. | Validate a candidate key on independent cryptographic examples. Distinguish key extraction from copying or reproducing a keyed computation. |
| **18. Behavioral modeling** | Design controlled input sequences, record starting state and environment, and vary one relevant condition at a time. Include transitions, failures and timing where they affect behavior. | Reserve additional cases for testing predictions. Report the states and inputs covered; several internal implementations may explain the same observations. |

Frida supports observation of calls and accessible memory, while the PE specification explains why a process image differs from a file on disk. These support different stages of recovery and should not be treated as interchangeable tools. [Frida API documentation](https://frida.re/docs/javascript-api/), [Microsoft PE specification](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format)

**Rehosting should carry an explicit model of the environment.** Ghidra documents limitations in using its instruction semantics for emulation. HALucinator shows how replacing hardware abstraction functions can make firmware analysis tractable, while Renode provides saved emulation state for repeatable experiments. None of those mechanisms supplies a missing hardware secret merely by simulating a successful API response. [Ghidra emulation caveats](https://ghidra.re/ghidra_docs/GhidraClass/Debugger/B2-Emulation.html), [HALucinator research](https://www.usenix.org/conference/usenixsecurity20/presentation/clements), [Renode state saving](https://renode.readthedocs.io/en/latest/basic/saving.html)

The published Syntia and DCA results remain useful, but their scope needs preserving: one demonstrated semantic reconstruction for evaluated obfuscated computations; the other demonstrated key recovery from the white-box implementations studied. Neither establishes an automatic result for every protected application. [Syntia](https://www.usenix.org/conference/usenixsecurity17/technical-sessions/presentation/blazytko), [DCA](https://eprint.iacr.org/2015/753)

For **hardware acquisition and physical analysis**, stronger evidence requirements are especially useful because a technically successful acquisition can still yield the wrong representation:

| Method | Stronger analytical procedure | Validation and main limitation |
|---|---|---|
| **19. External raw flash acquisition** | Record device identity, geometry, read mode, page/spare layout, ECC handling and bad-block treatment. Preserve raw data separately from corrected or reconstructed output. | Compare repeated reads and independently check interpretation where possible. Identical reads can still share a systematic error; a correct dump may contain only ciphertext. |
| **20. Managed storage acquisition** | Identify the logical areas exposed by the controller, their geometry and any omitted regions. Distinguish controller management, authentication and encryption. | Validate logical-image identity and coverage. The host view does not necessarily expose physical NAND layout or controller secrets. RPMB protection alone does not establish confidentiality. |
| **21. Debug and recovery interfaces** | Establish the interface’s actual capabilities, enabled security domains and readable address ranges. Use documented behavior to distinguish logging, update-only access and memory readback. | Verify known regions and record inaccessible regions. One successful read does not imply access to all CPUs, secure memory or key storage. |
| **22. Bus and execution trace** | Identify which side of a decryption boundary is observable. Preserve timing and decoding assumptions, and correlate transactions with known device activity. | Confirm protocol decoding against independent structure or behavior. An external bus may carry ciphertext, while execution trace may reveal addresses without revealing data values. |
| **23. RAM, DMA and remanence** | Establish when relevant material exists and which memory is actually captured. Look for structured cryptographic state as well as raw key bytes. | Validate candidates against independent correct cryptographic examples. Missing pages, memory encryption, isolation, scrubbing and acquisition timing limit conclusions. |
| **24. Power, EM, timing and cache analysis** | Define the leakage hypothesis, repeatability requirements and environmental controls. Keep data used to tune the analysis separate from data used to confirm it. | Require independent confirmation of recovered information. A statistical peak is not a validated key. Countermeasures must be assessed against the particular leakage channel. |
| **25. Fault injection and DFA** | Separate induced malfunction, a useful fault model and secret recovery. Determine whether observed results actually fit the assumed model. | Validate any recovered key using independent correct input/output pairs. Matching faulty behavior is a separate claim; crashes and resets alone do not establish cryptanalytic progress. |
| **26. Invasive silicon analysis** | Define the specific physical observation needed—layout, internal signal, memory state or interconnect—and how it would map to logical information. | Check interpretations against known structures or independent device behavior. Seeing cells or signals does not itself reveal plaintext or an accurately decoded key. |

The NAND distinction is supported by the kernel’s separate raw and ECC-related interfaces. For managed storage, authentication and replay protection must be distinguished from encryption applied by another layer. OP-TEE’s storage architecture illustrates how multiple mechanisms can be combined. [Linux NAND documentation](https://www.kernel.org/doc/html/v4.19/driver-api/mtdnand.html), [OP-TEE secure storage](https://github.com/OP-TEE/optee_docs/blob/master/architecture/secure_storage.rst)

**Key-schedule forensics deserves explicit treatment within method 23.** Cryptographic implementations may keep expanded keys or other related state in memory. That redundancy can help identify candidate keys or reconstruct damaged material. Cold-boot research and later work using learning and constraint solving demonstrate this under particular acquisition and error models. These methods start with leaked memory information; they do not recover a protected key from ciphertext alone. [Original cold-boot research](https://www.usenix.org/legacy/event/sec08/tech/full_papers/halderman/halderman_html/), [Zimerman and colleagues, 2021](https://proceedings.mlr.press/v139/zimerman21a.html)

Constant-time code also needs precise interpretation. It addresses secret-dependent timing behavior under an execution model. It is not a universal statement about power or electromagnetic leakage. Those channels require their own assessment and countermeasures. [BearSSL constant-time discussion](https://www.bearssl.org/constanttime.html)

For **cryptographic weaknesses and implementation defects**, the strengthened methods are:

| Method | Stronger analytical procedure | Validation and main limitation |
|---|---|---|
| **27. Passwords and constrained key spaces** | Establish how candidate secrets become keys, including encoding, KDF, salt and cost parameters. Estimate work using measured verification cost and a defensible candidate space. | Use a reliable candidate verifier. Key length alone says little about password uncertainty, while a properly generated random AES key has a fundamentally different search space. |
| **28. Mode and nonce misuse** | Identify the exact construction and establish whether repeated values occur under the same key in circumstances that violate its requirements. Distinguish reused data from fresh encryption of different messages. | Validate the predicted confidentiality or authentication failure. GCM’s authentication subkey, an exposed keystream and the AES encryption key are different results. |
| **29. Chosen-input and response oracles** | Establish that controllable inputs reach the relevant operation and produce a repeatable, meaningful observable difference. Account for state, timing noise and earlier validation stages. | Confirm the inferred information independently. Different errors are not automatically a useful oracle; uniform error text does not exclude timing leakage. |
| **30. Implementation vulnerabilities** | Test the actual reachable parser, loader or key-management boundary. Preserve the conditions needed to reach it and minimize reproducible failures. | Report a crash as a defect. Firmware disclosure, key exposure or an altered security decision each requires its own evidence. A harness that skips a real prerequisite cannot establish production reachability. |
| **31. Algorithm-level cryptanalysis** | State the attack model and required data, queries, related keys, memory and computation. Check that these assumptions match what is actually available. | Demonstrate the claimed result and calculate practical resource requirements. Beating exhaustive search mathematically may still leave an infeasible recovery task. |

NIST’s mode review documents why misuse must be assessed at the construction level. Joux’s GCM work concerns the keyed hash used for authentication; it should not be described as direct recovery of the AES key. [NIST mode review](https://nvlpubs.nist.gov/nistpubs/ir/2024/NIST.IR.8459.pdf), [Joux’s GCM analysis](https://csrc.nist.gov/csrc/media/projects/block-cipher-techniques/documents/bcm/joux_comments.pdf)

Similarly, the full-AES biclique paper explicitly places its results outside practical attacks on AES. “Less work than brute force” and “feasible for this investigation” are separate conclusions. [Biclique cryptanalysis of AES](https://eprint.iacr.org/2011/449)

Four further improvements make the methods more useful together.

**First, maintain an exact map of authentication coverage.** Record which bytes are signed or authenticated, which key establishes trust, and which transformations happen before or afterward. MCUboot documents verification over unencrypted image data. UEFI’s firmware-management implementation describes a signature covering payload data and a monotonic count. A valid outer signature cannot automatically validate every later interpretation of the contents. [MCUboot encrypted-image design](https://docs.mcuboot.com/encrypted_images.html), [UEFI firmware-management implementation](https://github.com/tianocore/edk2/blob/master/FmpDevicePkg/Readme.md)

**Second, treat reuse of the original transformation code as a distinct implementation option.** Once a suitable reader or decryptor is available, a narrowly scoped offline execution of that original component may preserve details that an independent rewrite would miss. The experiment still needs the real dependencies and valid inputs. Comparing an independent implementation with the original on several cases provides stronger evidence than either implementation’s own round-trip test.

**Third, add architecture-specific treatment for FPGA configuration.** An encrypted FPGA bitstream is not necessarily a CPU executable that will appear intact in process memory. Analysis must account for the configuration engine, on-chip decryption, authentication, key storage and permitted readback. AMD’s UltraScale documentation describes AES-GCM and BBRAM/eFUSE key storage, illustrating why the ordinary “dump the unpacked executable” model does not transfer directly. Recovering configuration also does not automatically recover the original HDL. [AMD bitstream encryption architecture](https://docs.amd.com/r/en-US/xapp1267-encryp-efuse-program/Encrypted-Bitstream-Implementation-Overview), [AMD key storage](https://docs.amd.com/r/en-US/xapp1267-encryp-efuse-program/AES-Key-Storage)

**Fourth, make repeatability and independent checks part of every method.** Record tool versions, input hashes, offsets, parameters, captured state and unobserved regions. Use additional inputs or artifacts to test conclusions that were developed on the first sample. AI-generated names, structures and pseudocode remain hypotheses until checked against these records.

A useful ordering is therefore based on **available access, information gained and validation cost**, rather than a fixed ladder:

1. Establish artifact identity and the representation being examined.
2. Resolve packaging, compression, delta and storage-format questions.
3. Identify the component that consumes the material and its secret dependencies.
4. Choose the shortest available route to the required result—static analysis, supported readback, runtime observation or focused rehosting.
5. Reproduce the relevant transformation and validate it independently.
6. Consider specialist physical or cryptanalytic methods when their prerequisites and expected result are clear.

A supported readback path on a test unit may be simpler than weeks of decompilation. Conversely, physical access is not useful for plaintext recovery if the accessible boundary exposes only ciphertext.

The acceptance standard should remain explicit:

- **A valid original authentication tag or trusted signature** can confirm the covered result, subject to the format and trust assumptions.
- **A trusted expected digest or independent reference artifact** can establish exact byte agreement for its stated scope.
- **Structural consistency and reference behavior** provide corroboration with identifiable coverage limits.
- **Readable strings, plausible disassembly, successful loading and same-key round trips** are preliminary checks.

For a reversible cipher operation, decrypting with a guessed key and re-encrypting with that same key can reproduce the original ciphertext even when the guess is wrong. A standard test vector can confirm that an analysis tool implements AES correctly without proving that it has identified this firmware’s key, mode or layout. The strengthened workflow makes those distinctions part of every recovery claim.
